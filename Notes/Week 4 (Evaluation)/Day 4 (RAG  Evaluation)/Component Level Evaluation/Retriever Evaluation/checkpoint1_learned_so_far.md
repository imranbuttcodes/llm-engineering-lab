# 🧠 RAG Evaluation — Everything We've Learned So Far

## 0. The Big Picture: What Are We Evaluating?

We established that an LLM/RAG application isn't one single thing to evaluate.

We can evaluate at different levels:

### Level 1 — Component-level evaluation

Evaluate individual components independently.

Examples:

* Retriever
* Reranker
* Generator / LLM
* Embedding model
* Chunking strategy
* Query transformation
* etc.

### Level 2 — Pipeline-level evaluation

Evaluate how components work **together**.

For RAG:

```text
Question
   ↓
Query Processing
   ↓
Retriever
   ↓
Reranker
   ↓
Context
   ↓
LLM
   ↓
Answer
```

We evaluate whether the **pipeline as a whole** produces good retrieval + generation behavior.

### Level 3 — Application/System-level evaluation

Evaluate the complete application from the user's perspective.

Things such as:

* Answer quality
* Correctness
* Groundedness
* Safety
* Reliability
* Latency
* Cost
* Failure handling
* User experience
* Production behavior

So:

```text
Component
   ↓
Pipeline
   ↓
Whole Application/System
```

# 4. Precision vs Recall

We learned the fundamental tradeoff.

## Recall

> **Did we retrieve the relevant information that we needed?**

High recall:

```text
Relevant information
       ↓
Retriever finds it
```

Low recall:

```text
Relevant information exists
       ↓
Retriever misses it
```

---

## Precision

> **Of what we retrieved, how much was actually relevant?**

High precision:

```text
Retrieved:
[Relevant]
[Relevant]
[Relevant]
```

Low precision:

```text
Retrieved:
[Relevant]
[Irrelevant]
[Irrelevant]
[Irrelevant]
```

---

# 5. Precision–Recall Tradeoff

We explicitly discussed:

> **Recall and Precision Tradeoff**

Increasing retrieval breadth can improve recall but introduce more irrelevant context.

Conceptually:

```text
Higher K
   ↓
More retrieved chunks
   ↓
Potentially ↑ Recall
   ↓
Potentially ↓ Precision
```

And:

```text
Lower K
   ↓
Fewer chunks
   ↓
Potentially ↑ Precision
   ↓
Potentially ↓ Recall
```

So `top_k` is an important retrieval hyperparameter.

# 6. Reference-Based vs Reference-Free Evaluation

We also discussed this distinction.

## Reference-based evaluation

There is some form of ground truth/reference.

Examples:

```text
Question
Expected Answer
Relevant Information
```

The evaluator compares the system against that reference.

---

## Reference-free evaluation

The evaluator does not necessarily require a predefined golden answer.

Instead it judges things such as:

* Is the answer supported by the retrieved context?
* Is the response relevant?
* Is the context useful?
* Is the answer grounded?

This distinction became particularly important when discussing DeepEval's contextual metrics.

# 7. Golden Dataset

A golden dataset contains evaluation questions and their stable ground truth.

Typical structure:


### Method 1 — Human authored

Highest control, but expensive.

### Method 2 — LLM-assisted drafting + human review


This reduces manual effort while retaining human validation.

---

### Method 3 — DeepEval Synthesizer + Human Review

Use DeepEval's dataset synthesis capabilities to generate evaluation cases, then have humans validate them.

Take real production questions:

```text

        ↓
Filter / clean
        ↓
Create expected answers / references
        ↓
Golden dataset
```

This makes the evaluation dataset representative of real usage.


# 13. Context Verification

The judge examines the retrieved chunks and asks:

> **Does the retrieved context contain enough information to support the claims in the ideal answer?**

Conceptually:

```text
Ideal Answer
     ↓
Atomic Claims
     ↓
Retrieved Context
     ↓
Claim supported?
     ↓
Yes / No
```

This is the conceptual model we used to understand **Contextual Recall**.

---

# 14. Contextual Recall

We learned that DeepEval's contextual recall evaluates whether the retrieved context contains the information needed to support the expected answer.

Conceptually:

```text
Expected Answer
      ↓
Atomic Claims
      ↓
Retrieved Context
      ↓
How many claims are supported?
```

So:

```text
High Contextual Recall
=
Retriever retrieved enough information
to support the expected answer.
```

---

# 15. Contextual Precision

Then we learned the complementary concept.

Instead of:

> Did we retrieve enough useful information?

Contextual precision asks approximately:

> **How much of the retrieved context is actually useful/relevant to the expected answer, and is it ranked appropriately?**

Conceptually:

```text
Retrieved Context
       ↓
Evaluate relevance of retrieved chunks
       ↓
Relevant vs irrelevant
       ↓
Ranking matters
```

So:

```text
Contextual Recall
→ Did we get the necessary information?

Contextual Precision
→ Did we avoid unnecessary/irrelevant retrieved information
  and rank useful information appropriately?
```

# 23. Deterministic Retriever Metrics

We also discussed classic retrieval metrics:

### Precision@K

How many of the top K retrieved items are relevant.

```text
relevant retrieved
────────────────────
        K
```

### Recall@K

How much of the relevant information was retrieved within K.

### Hit Rate@K

Did at least one relevant item appear in top K?

Conceptually:

```text
1 → yes
0 → no
```

### MRR — Mean Reciprocal Rank

Measures how high the **first relevant result** appears.

If the first relevant result is:

```text
rank 1 → 1
rank 2 → 1/2
rank 3 → 1/3
rank 4 → 1/4
```

Then average across queries.

### NDCG

**Normalized Discounted Cumulative Gain.**

Unlike simple relevance matching, it accounts for:

* relevance level
* ranking position

So ranking matters.

# 33. Contextual Recall vs Retriever Recall

This distinction is **very important**.

### Traditional Recall@K

Usually needs explicit relevance labels:

```text
Did retrieved item match known relevant item?
```

### Contextual Recall

Uses the expected answer and retrieved context semantically:

```text

      ↓
Claims
      ↓
Retrieved Context
      ↓
Are claims supported?
```

Therefore contextual recall is more **content/semantic based** and less dependent on specific chunk IDs.
